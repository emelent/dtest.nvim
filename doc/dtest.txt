1. INTRODUCTION                                           *dtest-introduction*

dtest.nvim runs the tests of a .NET solution or project from inside Neovim
and shows them as a tree over a log, the way vitest does. It drives the
`dotnet` CLI: it builds the target once, lists every test with
`dotnet test --list-tests`, and runs whatever the tree selects while the
panes update live.

It is a port of the dtest terminal app, and keeps its layout, its keys and
its colours.

==============================================================================
2. REQUIREMENTS                                           *dtest-requirements*

- Neovim 0.10 or newer.
- The `dotnet` SDK on $PATH, with test projects using the VSTest runner
  (Microsoft.NET.Test.Sdk with xUnit, NUnit or MSTest).

No other plugins are needed.

==============================================================================
3. COMMANDS                                                   *dtest-commands*

                                                                      *:Dtest*
:Dtest [target]         Open the panes for a solution (.sln, .slnx) or
                        project (.csproj, .fsproj, .vbproj) file. With a
                        directory, or with no argument at all, a solution
                        file in that directory is used, or else the first
                        project file there. Opening while the panes are
                        already open jumps to them.

                                                                *:DtestToggle*
:DtestToggle            Show the panes, or hide them when they are up.
                        Hiding keeps the session: see |dtest-hiding|.

                                                                 *:DtestClose*
:DtestClose             End the session: stop whatever dotnet is doing and
                        give up the results. To put the panes away for a
                        while, hide them instead; see |dtest-hiding|.

                                                                   *:DtestRun*
:DtestRun               Run every test, opening the panes first if needed.

                                                             *:DtestRunFailed*
:DtestRunFailed         Re-run the tests that failed last time.

                                                                  *:DtestFile*
:DtestFile[!]           Run every test the file in the current buffer
                        declares. The cursor stays where it is; with !, it
                        goes to the panes. See |dtest-from-source|.

                                                               *:DtestNearest*
:DtestNearest[!]        Run the test the cursor is in. Above the first
                        test of a class, the class is what runs. The cursor
                        stays where it is; with !, it goes to the panes.
                        See |dtest-from-source|.

                                                                *:DtestFolder*
:DtestFolder[!] [path]  Run a folder of tests. Without {path} it asks
                        which, in Snacks' picker when that is installed
                        and in |vim.ui.select()| otherwise. The cursor
                        stays where it is; with !, it goes to the panes.
                        See |dtest-folders|.

                                                                *:DtestReload*
:DtestReload            Rebuild and list the tests again.

4. LUA API                                                         *dtest-api*

                                                             *dtest.setup()*
require('dtest').setup({opts})
                        Merge {opts} over the defaults and define the
                        highlight groups. Optional: the defaults stand
                        without it. See |dtest-configuration|.

require('dtest').open({target})         Open the panes. |:Dtest|
require('dtest').toggle()               |:DtestToggle|
require('dtest').hide()                 take the panes off the screen,
                        keeping the session
require('dtest').show({opts})           put them back; {opts.focus} puts
                        the cursor in them too
require('dtest').close()                |:DtestClose|
require('dtest').run_all()              |:DtestRun|
require('dtest').run_failed()           |:DtestRunFailed|
require('dtest').reload()               |:DtestReload|
require('dtest').is_open()              Whether the panes are on screen.
require('dtest').has_session()          Whether there is a session at all,
                        shown or hidden.

5. LAYOUT                                                       *dtest-layout*

The panes open beside the window |:Dtest| was called from, so the code
stays on screen. Which way round they go follows the shape of the space
they are given, and is re-checked when the terminal is resized: >

    wide space                       tall space
    +--------+-----------+           +---------------------+
    | Tests  | Log       |           | Log           70%   |
    |  30%   |  70%      |           +---------------------+
    +--------+-----------+           | Tests         30%   |
    | Ran 8 tests        |           +---------------------+
    +--------------------+           | Ran 8 tests         |
                                     +---------------------+
<
A cell is about twice as tall as it is wide, so a space counts as wide
once it has at least 2.5 columns per line. `layout.direction` pins either
arrangement; `layout.position` and `layout.size` say where the space comes
from and how much of the window is given up to it. Beside the code the
panes take a fifth of it, as a sidebar does; under it, two thirds, there
being no code alongside to crowd. Neither goes below what can be read.

Log     The larger pane, 70%. The results of whatever the tree selects:
        for a test its verdict, message, failing location, stack trace and
        output; for a group every failure beneath it. Build errors come
        first. It is an ordinary buffer, so Neovim's motions, search and
        yanking all work in it.

Tests   The other 30%: projects, classes, methods and theory rows under a
        root that stands for the solution, with counts and durations
        rolled up. Moving the cursor here is what changes the log.

Summary Two lines along the bottom, spanning both panes: what the batch
        was, and how it went. A message from dtest takes the first of the
        two while it has something to say.

The buffers carry the filetypes `dtest-tree`, `dtest-log` and
`dtest-summary`.

6. MAPPINGS                                                   *dtest-mappings*

Press `?` in the tree for the list with whatever keys are bound. Motions
are Neovim's own in whichever pane has focus.

    <C-j> <C-k> <Tab>   switch between the log and the tree
    l / h               expand / collapse a project, class or theory
    L / H               expand / collapse the whole tree
    <Space>             toggle a fold
    i / I               focus on the selected project or class; step out
    <CR> r              run the selected node
    A                   run the whole solution, or whatever is in focus
    F                   re-run only the failed tests
    f / s               show only the failed / skipped tests
    a                   show all tests again (<Esc> too)
    x                   cancel the running tests and drop the queue
    n / N               next / previous failed test
    o                   open the source of what is selected
    t /                 filter the tree by name as you type
    v                   show the raw dotnet output instead of the results
    <C-r>               rebuild and list the tests again
    ?                   help; any key closes it
    q                   hide dtest, keeping the session

The tree-only keys (l, h, n, N, /, f, s, a, i, t, <Space>) are bound in the
tree pane alone, so the log keeps Neovim's search and motions.

`o` opens, in the window dtest was opened from: the file and line named by
the log line under the cursor when it is a stack frame, else a failed
test's failing line, else the declaration of what is selected, found by
scanning the project's sources.

                                                              *dtest-hiding*
Hiding, and coming back ~

Hiding is not closing. |:DtestToggle|, and `q` in the panes, takes the
windows off the screen and leaves everything else standing: the tree, the
results, the logs, and any `dotnet test` still going. Toggling again puts
them back, beside whatever is being edited then rather than where they
were before.

A run left going behind hidden panes shows them again once every test of
it is in, without taking the cursor. A run asked for while they are hidden
stays hidden until it finishes, which is the point of putting them away.

|:DtestClose| is what ends a session.

                                                             *dtest-folders*
Folders of tests ~

A folder is a namespace under a project, and the project itself. .NET lays
namespaces out as directories by convention, so these are the folders of
the test tree. |:DtestFolder| lists them with what each one holds, counting
everything beneath it: picking `Orders` runs `Orders/Validation` too.

A project runs unfiltered; a namespace runs as one
`FullyQualifiedName~Ns.` filter rather than one expression per class.
Afterwards the tree is focused on what ran, its classes opened.

With Snacks installed the list is its picker, under the source name
`dtest_folders`, so `Snacks.picker.config.sources.dtest_folders` can change
its layout or keys. Without it, |vim.ui.select()| is used, which is
whatever the editor has been told to use for a choice.

                                                          *dtest-from-source*
Running from the file you are editing ~

|:DtestFile| and |:DtestNearest| work from a source buffer rather than from
the tree.

:DtestNearest takes the nearest test declaration at or above the cursor. An
attribute line counts as part of the test under it, so [Fact] and [Theory]
do the expected thing; above the first test of a class, the class runs. A
theory runs all of its rows, a single row having no name of its own.

Which tests a buffer holds is worked out from the classes it declares and
the names dotnet already listed, so a helper or a call to another test is
never mistaken for one. The buffer is read, not the file on disk.

Both take you to the panes, opening them beside the buffer when they are
closed, and focus the tree on what the file holds: the class it declares
becomes the root of the tree, as the focus key does, with every test under
it unfolded, theory rows included. The run that follows leaves those folds
alone instead of closing the passing groups, since opening them was the
point; a later run started from the panes folds as usual. A file declaring
several classes focuses the project they share.

A buffer holding nothing dtest knows about is the exception: there is
nothing to watch, so it says so and leaves you where you are.

With ! (or `focus = false`) the run happens in the background: the cursor
stays in the code and the outcome is echoed when it ends. That line is
echoed after any run whose panes are not the tab being looked at.
>lua
    vim.keymap.set('n', '<leader>tt', function() require('dtest').run_nearest() end)
    vim.keymap.set('n', '<leader>tf', function() require('dtest').run_file() end)
<
When the panes are closed and nothing is configured, these look for a
solution in the working directory first and then upwards from the file
itself, so they work from a buffer whose project is nowhere near it.

7. CONFIGURATION                                         *dtest-configuration*

>lua
    require('dtest').setup({
      target = nil,          -- solution or project file; nil looks in the cwd
      configuration = nil,   -- build configuration passed to dotnet (-c)
      no_build = false,      -- list and run against existing binaries
      build_on_open = true,  -- build once when the panes open
      layout = {
        direction = 'auto',  -- 'auto' | 'vertical' | 'horizontal'
        position = 'auto',   -- 'auto' | 'right' | 'left' | 'below' | 'above'
        size = nil,          -- a fifth beside the code, two thirds under it
        log_ratio = 0.7,     -- the log's share, the tree taking the rest
        footer = true,       -- the two summary lines
      },
      icons = { passed = '✓', failed = '×', skipped = '↓', none = '·',
                queued = '⧗', arrow = '❯', open = '▾', closed = '▸',
                rule = '⎯', spinner = { '⠋', '⠙', '⠹' } },
      colors = {
        passed  = { fg = '#87af87', ctermfg = 108 },
        failed  = { fg = '#af5f5f', ctermfg = 131 },
        skipped = { fg = '#af875f', ctermfg = 137 },
        running = { fg = '#5fafaf', ctermfg = 6 },
        dim     = { fg = '#6c6c6c', ctermfg = 8 },
        badge   = { fg = '#ffffff', ctermfg = 15 },
      },
      keys = { run = { '<CR>', 'r' } },
    })
<
A colour is either a highlight definition as |nvim_set_hl()| takes it, or
the name of a group to link to.

An action's key list replaces its default outright, so rebinding one never
disturbs another; an empty list unbinds it. The actions are: >
    switch-pane  expand  collapse  expand-all  collapse-all  toggle-fold
    focus  unfocus  run  run-all  run-failed  only-failed  only-skipped
    show-all  clear  cancel  next-failure  previous-failure
    open-in-editor  filter  toggle-output  reload  help  quit
<

8. HIGHLIGHTS                                               *dtest-highlights*

Every group is derived from the six colours above and defined with
`default = true`, so a colourscheme or your own |:highlight| wins.

    DtestPassed DtestFailed DtestSkipped DtestRunning DtestQueued
    DtestDim DtestBold DtestKey DtestRule DtestCommand DtestError
    DtestExpected DtestActual DtestLocation DtestElapsed
    DtestQuick DtestSlow DtestQuickUnit DtestSlowUnit
    DtestTreePassed DtestTreeFailed DtestTreeSkipped DtestTreeRunning
    DtestTreeQuick DtestTreeSlow DtestTreeQuickUnit DtestTreeSlowUnit
    DtestBadgeFail DtestBadgeInfo DtestCursorLine DtestCursorLineNC

The tree wears a faded shade of each colour, so the summary is the line
that carries.

==============================================================================
9. HOW RUNS WORK                                                  *dtest-runs*

Running the root is one `dotnet test` over the solution. Anything smaller
is one `dotnet test` per project, with `--filter`:
`FullyQualifiedName~Ns.Class.` for a class, `FullyQualifiedName=Ns.Class.M`
for a method. A theory row cannot be addressed on its own, so running one
runs its method. Runs queue up, and everything queued since the last idle
moment is one batch, which is what the summary reports.

Results arrive twice over: from the console logger line by line as they
happen, and in full — messages, stack traces, captured output — from the
.trx files the run leaves behind. A test that was never listed still
appears, filed under the project whose name its own prefixes.
